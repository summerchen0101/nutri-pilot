# ECPay Payment Spec

> 介接密鑰、測試／正式端點、CheckMac、官方文件連結 → [ecpay-integration-handbook.md](./ecpay-integration-handbook.md)

## Purpose

Integrate ECPay payment into the subscription order flow.

This payment flow is popup-based:

- the main site stays in the subscription journey
- payment is completed in an external popup window
- after payment, the popup redirects the main window back into the app flow

---

## Entry Route

### Checkout Entry

`GET /api/payments/ecpay/checkout?orderId={orderId}`

Purpose:

- validate whether the order can be paid
- prepare ECPay payment form fields
- return an auto-submit HTML page that posts to ECPay

This route is intended to be opened in a popup window.

---

## Preconditions

The order must satisfy:

- order exists
- order is not already paid
- order is not cancelled
- order total is greater than zero

If not, system may return errors like:

- `ORDER_NOT_FOUND`
- `ORDER_ALREADY_PAID`
- `ORDER_CANCELLED`
- `ORDER_FREE_NO_PAYMENT`

---

## Payment Flow

1. User is on subscription confirm page
2. User clicks “go to payment”
3. App opens popup to `/api/payments/ecpay/checkout?orderId=...`
4. Backend generates ECPay fields
5. Popup auto-submits form to ECPay
6. User completes payment in ECPay
7. ECPay sends server callback to `ReturnURL`
8. ECPay sends browser callback to `OrderResultURL`
9. Popup redirects main window back into app flow and closes itself
10. Main window shows updated order/payment state

---

## Main Request Fields Sent To ECPay

Typical fields:

- `MerchantID`
- `MerchantTradeNo`
- `MerchantTradeDate`
- `PaymentType = aio`
- `TotalAmount`
- `TradeDesc`
- `ItemName`
- `ReturnURL`
- `OrderResultURL`
- `ChoosePayment = ALL`
- `EncryptType = 1`
- `CheckMacValue`

Notes:

- `MerchantTradeNo` is generated by the system
- `TotalAmount` uses integer amount in TWD
- `ItemName` is built from order content summary

---

## Merchant Trade No

Purpose:

- correlate ECPay events back to internal order

Requirements:

- generated by our system
- max length 20 characters
- unique enough for payment correlation

---

## CheckMacValue

Purpose:

- verify request and callback integrity

Current implementation assumptions:

- sort fields by key
- exclude `CheckMacValue` itself
- use .NET-style URL encode
- use configured ECPay secret values

Implementation should use one shared helper for:

- request generation
- callback verification

## Callback Design

### ReturnURL

Route:
`POST /api/payments/ecpay/return`

Purpose:

- server-to-server callback from ECPay
- verify callback authenticity
- update internal order payment status

Behavior:

- if payment success: mark order as paid
- if payment failure: mark order as failed
- acknowledge ECPay properly

This route is for backend state update, not user navigation.

---

### OrderResultURL

Route (this project):
`POST {SUPABASE_URL}/functions/v1/ecpay-order-result?appOrigin={browser_origin}`

Purpose:

- browser-side callback from ECPay
- popup flow completion
- return HTML that redirects main window back into app

Behavior:

- validate callback payload (CheckMac)
- resolve internal order from `CustomField1`
- redirect opener to `{appOrigin}/shop?checkout=1&paymentDone=1&orderId=…` (or `paymentFailed=1`)
- close popup if possible; `postMessage` fallback

**Do not** point OrderResultURL at a Next.js route under `/shop/*` that requires auth middleware: ECPay cross-site POST does not send SameSite session cookies, so the handler never runs.

This route is for popup/browser flow control, not the primary source of payment truth.

---

## Internal Order State Updates

### On success

Update order to:

- `payment_status = paid`
- payment provider = ECPay
- save merchant trade no
- save provider trade no
- save paid timestamp
- save callback status
- save callback payload metadata

### On failure

Update order to:

- `payment_status = failed`
- save failure reason
- save callback status
- save callback payload metadata

---

## Metadata Persistence

Recommended metadata fields:

- merchant trade no
- provider trade no
- rtn code
- rtn message
- payment date
- callback payload
- last checkout time
- payment email sent timestamp

Purpose:

- debugging
- support traceability
- idempotency
- avoid duplicate notifications

---

## Email Integration

After successful payment:

- send order confirmation email
- mark email sent timestamp in metadata
- support idempotent retry behavior

Important:

- payment success email should not send repeatedly if callback fires more than once

---

## Popup UX Rules

The payment flow must remain popup-based.

The main page should:

- stay visible
- indicate that a popup was opened
- explain that user should complete payment there
- recover if popup is blocked or closed
- refresh or re-check order state after popup completion

Do not convert payment flow into a normal full-page redirect unless explicitly requested.

---

## Frontend Result States

After payment popup completes, the app may show:

- paid
- failed
- syncing/pending
- order not found

All of these should be handled gracefully in UI.

### Main window during payment (subscription flow)

`useEcpayPopup` shows `EcpayWaitingOverlay` while the ECPay popup is open and the client polls `GET /api/orders/{id}/summary`.

- **Immediate methods (e.g. credit card):** when `payment_status` becomes `paid`, the overlay closes and `onPaymentConfirmed` runs (often `reload`).
- **Deferred methods (ATM, convenience-store code):** ECPay posts to **`PaymentInfoURL`** (`POST /api/payments/ecpay/payment-info`); the backend sets `payment_status: pending` and sends a **pending-payment email** to the member (`metadata.ecpay.pending_payment_email_sent_at`, idempotent). The client then navigates to **`/subscription/complete?orderId=…&paymentPending=1`** for the “待繳費／入帳後訂單成立” UI.
- **ReturnURL** (`POST /api/payments/ecpay/return`) with `RtnCode === "1"` runs `markOrderPaidFromEcpay` when payment actually settles; the usual **paid** order-confirmation email uses `order_email_sent_at` (separate from the pending email).

---

## Implementation Guidance

- keep payment request generation centralized
- keep callback verification centralized
- separate backend callback responsibilities from browser popup return responsibilities
- use one canonical mapping from merchant trade no to order
- make the flow idempotent where possible
